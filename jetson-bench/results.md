# Jetson AGX Orin 64 GB: measurements

## Machine
JetPack 6.2.1 / L4T R36.4.7 · Python 3.10.12 (venv on a USB stick, /mnt/data/work/venv-sam) · CUDA 12.6 · TensorRT 10.3.0 · torch 2.8.0 (NVIDIA jp6/cu126 wheel), torchvision 0.23 · nvpmodel MAXN + jetson_clocks · free RAM ~57 GB of 61 GB (idle per tegrastats ~5.7 GB used without dropping the cache; after `sync; echo 3 > /proc/sys/vm/drop_caches` 2.9–3.2 GB, which is how Embedl and SAM 3.1 were measured) · disk: eMMC 30 GB free, USB stick 75 GB free. Notes:
- Precision: EfficientSAM3 runs as is through `Sam3Processor`: FP32 weights, no autocast; the builder enables TF32 for matmul/cuDNN. FP16/INT8 for EfficientSAM3 appears only at the export stage (TensorRT).
- Breakdown (20 frames, prompt person, mean over clips): image encoder RV-M 87 ms, TV-M 105 ms, EV-M 74 ms; text encoder + detector/mask decoder ~220 ms for all three. So ~70 % of the time is not the backbone: the text goes through MobileCLIP-S0 again every time, plus the decoder. Caching prompt embeddings (see "Export") should cut latency noticeably. Not measured yet.
- GPU memory (torch.cuda.max_memory_allocated): RV-M 1.40 GB, TV-M 1.43 GB, EV-M 1.39 GB (reserved 1.57–1.67 GB).
- The difference between clips is within 2 %: on the vertical 720×1280 clip (warehouse-team), TV-M is ~6 ms slower (325 against 319 ms); RV-M and EV-M show no difference (the model input is always 1008×1008).
- Model load time: TV-M/EV-M ~9 s, RV-M ~16 s (from the USB stick).
- Embedl SAM 3 (2026-10-20): the quantized Embedl QDQ-ONNX (opset 17, `embedl_sam3_quant.onnx` 1.6 MB + `.onnx.data` 3.1 GiB) was built in TensorRT 10.3 with `trtexec --fp16 --int8 --builderOptimizationLevel=5 --memPoolSize=workspace:4294967296 --timingCacheFile=... --saveEngine=...`: 67.5 min wall time (engine generation itself 48 min, then more builder passes), peak RSS 13.9 GiB (TRT: CPU peak 14.2 GiB, GPU 5.2 GiB), on the first attempt; level 3 was not needed. The engine is 927 MiB ("weights" in the table = engine), the timing cache 35 MiB; both are in `weights/embedl-sam3/`. Log: `logs/embedl_trtexec_build.log`. trtexec's own measurement (random inputs, 15 runs): GPU compute mean 238.9 ms (238.3–240.1). This is the lower bound.
- Embedl measurement: `bench_sam.py --model embedl --engine ...` (adapter `bench/embedl_trt.py`, code from Embedl AB's `infer_trt.py`), the same 3 clips × 4 prompts × (5 + 60) frames. Frame time = preprocess (resize to 924×924, normalization) + engine + postprocess (score = sigmoid(logit)·sigmoid(presence) > 0.5, resize of 264×264 masks to the frame, sigmoid > 0.5). Engine only (H2D + execute + D2H of all outputs, as in `infer_trt.py`): 250–254 ms on all prompts (busy-warehouse 253.8, the others 250.1). The remaining 25–40 ms is CPU glue and grows with the number of masks (person ~3 masks per frame → 291 ms). The engine's text branch runs on every frame; only tokenization is cached on the CPU. Threshold 0.5 = the `Sam3Processor` default (Embedl's demo uses 0.25).
- Embedl against EfficientSAM3: full SAM 3 in INT8 is on par with EV-M in time (277–291 against 289 ms), with a 924×924 input against 1008×1008 for EfficientSAM3. Engine load 13.6 s (927 MB from the USB stick after dropping the cache).
- Embedl RAM: the idle baseline is 2.9 GB, not 5.7 GB. Before each Embedl run we did `echo 3 > /proc/sys/vm/drop_caches`: after trtexec the nvmap driver held 7.7 GB of freed GPU memory in its page pool (`/sys/kernel/debug/nvmap/pagepool/page_pool_available_pages` = 2 010 907 pages). tegrastats counts it as used, and new GPU allocations would come from this pool without showing an increase. For EfficientSAM3 the cache was not dropped, so absolute peaks are not comparable; compare Δ (Embedl 2.5 GB against 1.4 GB). EfficientSAM3's Δ may be understated for the same reason. Not checked.
- SAM 3.1 (2026-10-21): the official `facebookresearch/sam3` code (main, commit 7f473cf, not installed as a package, via `PYTHONPATH`), `build_sam3_image_model(checkpoint_path=weights/sam3.1/sam3.1_multiplex.pt, load_from_HF=False)` + `Sam3Processor` (threshold 0.5, input 1008×1008), Python 3.10 (the README requires 3.12; it works on 3.10 without changes). The same 3 clips × 4 prompts × (5 + 60) frames, both precisions in full (60 frames; FP32 did not need shortening: ~4.5 min per clip). Logs: `logs/sam3.1-{fp32,bf16}_<clip>.{log,json}`.
- The SAM 3.1 checkpoint is one file for the detector and the tracker: `detector.*` 854.7 M parameters (3265 MiB FP32), `tracker.*` 19.6 M (75 MiB). The image model takes only `detector.*`. 4 keys `backbone.vision_backbone.convs.3.*` were missing: this is the ×0.5 FPN level, which SAM 3.1 (tri-neck, scales 4/2/1) does not have. The image model drops this level anyway (`scalp=1`), so it is computed but not used. 36 extra keys (`interactive_convs`, `propagation_convs`, the tracker branches) were ignored. Masks were checked by eye (`samples/sam3.1-fp32_*.jpg`): people, vests, forklifts and the hard hat are segmented correctly.
- FP32: in the upstream ViT MLP (`perflib/fused.addmm_act`), fc1+GELU is hard-cast to bf16, and without autocast the model fails: `RuntimeError: mat1 and mat2 must have the same dtype, but got BFloat16 and Float`. For the FP32 reference, `bench_sam.py` replaces `addmm_act` with the same math in FP32 (`F.linear` + exact GELU); matmul runs in TF32 (the builder enables TF32 itself). This is the reference for IoU. BF16: `torch.autocast("cuda", dtype=torch.bfloat16)` around `set_image`/`set_text_prompt`, as in the SAM 3 examples, upstream code without replacements. BF16 masks match FP32: union IoU 0.995–0.999, instance 0.996–0.999 (see "Quality"). FP16 was not tried because BF16 worked right away.
- Breakdown (20 frames, person, mean over clips): image encoder FP32 778 ms / BF16 345 ms; text encoder + detector/decoder 250 / 172 ms. Time barely depends on the prompt and the clip (the input is always 1008×1008; in FP32 the vertical operator clip is ~20 ms slower, in BF16 there is no difference).
- SAM 3.1 memory: `torch.cuda.max_memory_allocated` FP32 4.25 GB, BF16 4.62 GB (the weights stay FP32, autocast keeps bf16 copies). Before each run `sync; echo 3 > /proc/sys/vm/drop_caches`; idle baseline per tegrastats 2.87–2.91 GB (Ollama idle, GUI running); peak 10.35–10.47 GB, Δ 7.46–7.57 GB. The peak is the maximum over the whole run including load (`torch.load` of the whole 3.3 GB file into RAM plus the model on the GPU in the same unified memory); the working level after load was not measured separately. Model load 28.5 s.
- SAM 3.1 against Embedl: Embedl SAM 3 INT8 (TRT) 277–291 ms against 513 ms for SAM 3.1 BF16 in PyTorch (1.8 times faster) and 1023 ms in FP32. Weights in the table are the checkpoint file size (detector + tracker).

Clip warehouse-team (720×1280), 5 warm-up frames + 20 frames, cache dropped before each run. Logs: `logs/combo-*_pexels-15170997-warehouse-team.{log,json}`.

- Embedl: the engine fuses the image encoder and the text branch into one call, so the image cannot be cached separately. Three prompts = three full calls. 291 ms is the mean for person over the 3 clips (277–291 ms across prompts), so 831–873 ms per frame.
- EfficientSAM3 BF16 is an extra data point (the single-prompt table has EfficientSAM3 in FP32 only): `--autocast bf16`; the number of masks found matches FP32 (person 1.75 against 1.70 per frame for EV-M, 2.00 against 2.05 for RV-M, forklift/vest the same). IoU of BF16 against FP32 for EfficientSAM3 was not computed.
- For EfficientSAM3, text+decoder (~220 ms FP32) costs 3 times more than the backbone, so one `set_image` per frame gains little. For SAM 3.1 the expensive encoder (343 ms) runs once: 853 ms against 3 × 513 = 1539 ms when calling the full seg for each prompt.
- Combo peak RAM: SAM 3.1 10.4 GB (Δ7.5), EfficientSAM3 5.7–5.9 GB (Δ2.8–3.0) with idle at 2.9 GB.

## Video mode (tracking)

SAM 3.1: `build_sam3_multiplex_video_predictor(checkpoint_path=sam3.1_multiplex.pt, use_fa3=False)` (the recommended entry point for SAM 3.1 multiplex; `build_sam3_video_predictor` builds SAM 3 without multiplex); the predictor enables BF16 autocast itself. Time per clip = `start_session` (mp4 decoding via OpenCV and resizing all frames to 1008×1008) + `add_prompt` + `propagate`, without model load (34–37 s). Cache dropped before each run, idle 3.1–3.2 GB. Frames with masks coloured by id (5 per clip, evenly spaced) are in `out/sam3.1-video/<clip>/frame_XXXX.jpg`, examples in `samples/sam3.1-video_*.jpg`. - Speed: 1.05–1.31 frames/s against 24–30 frames/s in the clip, so 19–29 times slower than real time (detector + tracker per frame, 0.76–0.95 s). Output comes in bursts: the median gap between frame outputs is 0.3–1.5 ms, p95 10.8–12.0 s. The predictor processes frames in groups (`batched_grounding_batch_size=16`), so the delay to the first mask of a frame reaches ~12 s.
- Memory grows with clip length: all frames of the clip sit on the GPU (1008×1008), plus tracker memory for each frame. `torch.cuda.memory_allocated` after `add_prompt` is 18.8–19.3 GB, then +9.7–13 MB per frame (busy-warehouse 18.8 → 24.6 GB, warehouse-team 19.3 → 28.1 GB); peak `max_memory_allocated` 27.0 / 38.7 / 35.2 GB (operator / warehouse-team / busy-warehouse). System peak RAM on warehouse-team is 52.0 of 61.4 GB: a 30 s clip at 30 fps is close to the limit on this board. Longer clips or a camera stream need a sliding-window mode (not tested). The script stops propagate if free memory is < 8 GB (it never triggered).
- `evict_cached_frame_outputs=True` (drop already returned full-resolution masks from the session cache) is on in all three runs. On operator without it the peak is 40.9 GB RAM and 28.4 GB allocated against 38.5 and 27.0 GB with it (`logs/sam3.1-video-noevict_*`); the time is the same (186 s propagate).
- Upstream bug workaround: `Sam3BasePredictor.start_session` passes `offload_state_to_cpu`, but `Sam3MultiplexTrackingWithInteractivity.init_state` does not accept that argument: `TypeError: ... init_state() got an unexpected keyword argument 'offload_state_to_cpu'`. In `video_sam.py` a wrapper drops the extra arguments; the sam3 code was not changed. The "Missing keys (64)" message at load is the RoPE buffers `freqs_cis_*`, which are computed, not loaded.
- EfficientSAM3, video: `build_efficientsam3_video_predictor` builds the EfficientSAM3 detector + the SAM 3 tracker (`build_tracker`) and expects `tracker.*` keys in the checkpoint. Our three `efficientsam3_ft/*.pt` (EV-M 799 tensors, RV-M 1183) contain only the detector (`backbone`, `transformer`, `geometry_encoder`, `segmentation_head`, `dot_prod_scoring`), no `tracker.*`. ### What had to be fixed in the graphs for TensorRT 10.3
1. **`If` around `scores.squeeze(-1)`**: the parser fails with `IIfConditionalOutputLayer inputs must have the same shape. Shapes are [-1,200] and [-1,200,1]`. The then branch (Squeeze) is inlined into the graph and the `If` is removed (`bench/onnx_inline_squeeze_if.py`; 1 node in open-vocab, 4 in fixed). The math is the same.
2. **FP16 gives NaN in all outputs** (also with the FP32 pinning of the `context_module` layers from PR #49). The cause is FP16 overflow in the ReLU linear attention of EfficientViT: on real frames |out| reaches 2.1·10⁵ while the FP16 limit is 65 504 (measured with hooks in PyTorch). The pinning from PR #49 (161 layers, `--precisionConstraints=obey --layerPrecisions/--layerOutputTypes`, list in `bench/trt_fp32_layers.py`) has no effect on TRT 10.3: both attention MatMuls go to a Myelin gemm with type Half (`logs/export_fp16mixed_layer_precisions_ev-m.log`). The fix (`bench/onnx_fp16_safe_linear_att.py`): relu(k)ᵀ is multiplied by 2⁻⁶, which is exact in FP32 and FP16. The numerator and denominator scale the same way, so the ratio does not change. eps 1e-15 (= 0 in FP16, which gives 0/0 where the denominator is 0; this happens on real frames) is replaced with 1e-4 in scaled units (6.4e-3 in the original units; the smallest non-zero denominator on the checked frames is ≈ 7). ORT FP32 before and after: score max|Δ| 1.7e-3, boxes ≤ 0.001 px. Only EfficientViT (EV-M) needs this; RepViT (RV-M) has no such attention.
3. **TensorRT computes the presence logit wrong**, in both FP32 and FP16. On frame 006 for `person`: ORT 6.97, TRT −0.32, so all scores are multiplied by about 0.42 and nothing is found. The head input (the presence token) matches ORT to 3e-3. I narrowed it down by bisection: when intermediate head tensors are exposed as outputs, the error disappears. Workaround (`bench/onnx_presence_fusion_break.py`): all LayerNorm/Add/Relu outputs of the presence head (`presence_token_out_norm` + `presence_token_head`, one per decoder layer) are declared as extra graph outputs: 36 in open-vocab, 144 in fixed. These are tensors of [1,1,256] and smaller, and the calling code ignores them. Exposing only the last activation was enough for the open-vocab graph but not for the fixed one. I did not find the real cause. These did not help: replacing the negative index `Gather(-1)` with 5, and `Slice[0:1]` with `Gather`.

Final graphs: `*_noif_fp16safe_pfb.onnx` (EV-M), `vision_decoder_noif_pfb.onnx` (RV-M). Engine check against PyTorch FP32 on frames 006 and 012: no NaN, the number of masks with score > 0.5 matches on all 4 prompts, for the found ones score max|Δ| ≤ 0.03; fixed-engine masks against PyTorch IoU 0.998–0.999 (`logs/export_trt_check_*.log`).

## Capacity
Formula: cameras = (1 / frame_latency_with_3_prompts, s) × 2 s. Latencies are the "three prompts per frame" measurements above (warehouse-team, 20–60 frames) and the TensorRT pipelines. One model copy, frames from all cameras are processed in turn, the GPU does nothing else, video decoding is not counted (at 0.5 frames/s per camera this is NVDEC and a fraction of a percent), no margin. For a deployment, plan a ~30 % margin (the "with margin" column = ×0.7). Calculated on 2026-10-21.

| Model / variant | ms per frame, 3 prompts | cameras on AGX Orin 64 GB | with 30 % margin | Orin NX 16 GB (estimate: AGX ÷ 1.7) |
|---|---|---|---|---|
| **SAM 3 INT8 (Embedl, TRT 10.3)** | 873 (3 × 291, text and image in one engine) | **2.3 → 2** | 1 | 1.3 → 1 |
| SAM 3.1 original, BF16 PyTorch | 853 | 2.3 → 2 | 1 | 1.4 → 1 (memory: +7.5 GB, a tight fit on 16 GB) |
| EfficientSAM3 EV-M, PyTorch FP32 | 731 | 2.7 → 2 | 1 | 1.6 → 1 |
| EfficientSAM3 EV-M, PyTorch BF16 | 501 | 4.0 → 3–4 | 2 | 2.3 → 2 |
| **EfficientSAM3 EV-M, TensorRT FP16, 4 classes + masks (fixed-class)** | 212 (4 classes at once) | **9.4 → 9** | 6 | 5.6 → 5 |
| EfficientSAM3 EV-M, TensorRT FP16, open-vocab, boxes only | 115 | 17.4 → 17 | 12 | 10 |
| EfficientSAM3 RV-M, TensorRT FP16, open-vocab, boxes only (4 prompts) | 170 | 11.8 → 11 | 8 | 6.9 → 6 |

What this means:
- **Full SAM 3** (Embedl INT8 or the original in BF16) on AGX Orin handles **2 cameras** at one frame every 2 s and three prompts; on Orin NX 16 GB, one. The quality is usable: people, vests, hard hats and forklifts are found (section "Quality").
- **EfficientSAM3** in PyTorch gives only 2–4 cameras, but after export to TensorRT FP16 it gives **9 cameras with masks (4 classes) or 17 without masks** on AGX, 5–10 on NX. But its quality on our clips is not usable for PPE rules (vests/hard hats are almost never found, person IoU on the forklift clips is 0.0–0.44), and the TensorRT engine does not change that: it reproduces PyTorch.
- Memory does not limit the number of cameras in any image-mode variant (1–7.5 GB increase per model copy, and cameras share one copy). Only SAM 3.1 video tracking is limited: +10–13 MB per frame, a 30-second clip took 52 GB of 61.
- The Embedl engine for SAM 3 on NX must be rebuilt on the NX itself (TensorRT engines are tied to the GPU); the build on AGX took 67 min.

## What did not work and why
- EfficientSAM3 EV-M: the first run failed with `ModuleNotFoundError: No module named 'omegaconf'` (import in `sam3/backbones/efficientvit/efficientvit/dc_ae.py`). Installed `omegaconf 2.4.0` in the venv (`pip install --no-cache-dir omegaconf`); after that all runs passed.
- SAM 3.1: `import sam3` failed with `ModuleNotFoundError: No module named 'triton'` (`sam3/model/edt.py` imports triton at package import; the video tracker also needs triton). Installed `triton 3.4.0` (the match for torch 2.8) from the NVIDIA index into the venv: `pip download triton==3.4.0 --no-deps --index-url https://pypi.jetson-ai-lab.io/jp6/cu126`, then `pip install --no-deps --no-cache-dir <whl>`; the wheel is 270 MB (deleted after install), 764 MB in the venv on the USB stick. A test triton kernel on Orin (sm_87) compiles and computes correctly.
- SAM 3.1 FP32: fails without autocast (`mat1 and mat2 must have the same dtype, but got BFloat16 and Float`) because upstream hard-codes fc1+GELU in the ViT MLP to bf16. Workaround in `bench_sam.py` (replacement with FP32); details in the latency notes.
- EfficientSAM3 → TensorRT 10.3 export: neither PR #49 graph gives a working FP16 engine without fixes. (1) The parser rejects the `If` around `squeeze(-1)` (`IIfConditionalOutputLayer inputs must have the same shape`). (2) FP16 gives NaN because of overflow in the EfficientViT linear attention; the FP32 pinning of `context_module` from PR #49 does not take effect on TRT 10.3, and the attention MatMuls stay in Half. (3) The presence logit is computed wrong in both FP32 and FP16. All three are worked around with ONNX graph fixes: `bench/onnx_inline_squeeze_if.py`, `onnx_fp16_safe_linear_att.py`, `onnx_presence_fusion_break.py`; details in "Export". I did not find the cause of (3); the workaround is to expose the intermediate presence head tensors as outputs. Replacing `Gather(-1)` with a positive index and `Slice[0:1]` with `Gather` did not help. This is probably a Myelin fusion bug in this TensorRT version; I did not check a newer one.
- The fixed-class graph with `--mask` outputs masks for all 800 queries at 1008×1008 f16, 1.6 GB per frame. trtexec copies them to the host in 86.7 ms; in `bench/trt_sam.py` they stay on the GPU and only the found ones are copied. Upsampling to 1008² and the sigmoid inside the graph cost ~50 ms of 205.
- I did not split the model into three graphs (image encoder / text encoder / decoder): PR #49 gives vision+decoder as one graph, so on a phone the backbone is recomputed for each prompt. RV-M was exported only as open-vocab (no fixed-class engine with masks and no ORT CPU run); TV-M was not exported, for lack of time.
